## Goal


Know how the engine handles local players, input and connections well enough to pick a splitscreen approach.

## Acceptance Criteria


- [x] Local-client limits mapped
- [x] Input paths mapped (keyboard, mouse, XInput)
- [x] Approach picked

## Notes

## Progress


- 2026-10-11 findings:
  - One local client is baked in: `MAX_LOCAL_CLIENTS 1` (cgame_mp/cg_local_mp.h:16), ~89 globals sized [1], 114 `x < 1` loops, ~125 literal `0` localClientNum calls, accessors assert `localClientNum == 0`. Splitscreen helpers are stubs (client/splitscreen.cpp:8 returns 1; GAMEMODE_LOCAL_SPLITSCREEN returns 0). Viewport math always full screen.
  - Input: keyboard/char hard-wired to client 0 (qcommon/common.cpp ~1097). Pads only polled when the window is foreground (win32/win_input.cpp:213-221) and only XInput user 0 (win32/win_gamepad.cpp). `gpad_enabled` default 0.
  - Server: several clients from 127.0.0.1 are fine (different port + qport). Ports auto-increment from 3074. No single-instance lock. Join with `connect 127.0.0.1:<port>`; host with `devmap <map>`. Risk: Steam auth ticket per account.
  - Windowed size: `r_customMode WxH`, `vid_xpos/vid_ypos`; borderless always fills the monitor (gfx_d3d/r_init.cpp:662).
- Decision: splitscreen as one game process per player on loopback, windows tiled on one monitor, each process bound to one input device. True in-process splitscreen would mean re-plumbing the ~300 single-client sites above (weeks); kept as an idea card.
